# Project Stewardship

Project Stewardship is the maintenance layer for keeping repositories coherent as they change.

The goal is not to create more process. The goal is to remove things people otherwise have to remember: propagating documentation changes, checking links, updating indexes, noticing stale files, keeping repository structure understandable, and surfacing maintenance work before drift becomes confusing.

## Principle

**Automate memory, not judgment.**

Automation should aggressively handle deterministic maintenance and conservatively surface semantic decisions.

### Safe to automate directly

- generated documentation indexes
- generated README sections
- link and path validation
- manifest/file inventory checks
- formatting and deterministic migrations
- dependency/cache metadata generated by tools
- test/status summaries
- known-safe cleanup with an explicit contract

### Review before changing

- rewriting explanatory documentation
- deciding whether a concept is obsolete
- merging or reorganizing overlapping documents
- renaming public concepts
- archiving project history
- deleting files whose relevance requires interpretation

### Never delete merely because something is old

Age is a review signal, not proof of irrelevance. Stale or apparently orphaned material should normally become a maintenance candidate or proposed PR before deletion.

## Repository maintenance contract

Each participating repository should eventually carry a small machine-readable maintenance manifest, for example:

```text
repo-maintenance.json
```

or a domain-specific equivalent such as a documentation manifest.

The contract can describe:

- maintained READMEs and documentation
- generated sections
- source paths that affect each document
- required indexes
- lifecycle state: active, review, deprecated, archived
- review cadence where useful
- files/directories intentionally excluded from cleanup
- deterministic repair commands
- project-specific checks

The contract should remain understandable without knowing the automation implementation.

## Event model

### Pull request

Fast feedback before change lands:

- run tests and repository contracts
- check generated files are synchronized
- validate links/references
- identify documentation affected by the diff
- report likely orphan/stale/conflicting files
- show a concise maintenance summary

### Push to main

Repair deterministic drift:

- regenerate indexes and machine-owned README sections
- commit safe deterministic repairs when configured
- refresh inventories/status artifacts

### Scheduled reconciliation

Catch slow drift that no single PR exposes:

- stale-document review dates
- orphaned or unreachable files
- broken cross-repo references
- dependency/workflow drift
- duplicated or superseded material
- missing READMEs/indexes
- repositories that have stopped receiving the current maintenance contract

Scheduled reconciliation should create a report, issue, or proposed PR rather than silently performing uncertain cleanup.

## Documentation propagation

Documentation should be treated as part of the dependency graph.

Example:

```text
workspace-model.js ─┐
workspace-store.js ─┼─> docs/DOCUMENTS_AND_PROJECTS.md ─> README.md
workspace-ui.js ────┘
```

When a source node changes, automation should know which documentation nodes deserve review. Deterministic portions can update automatically. Semantic portions are surfaced as review candidates.

This prevents the common failure mode where a leaf document is updated but parent READMEs and indexes remain stale.

## Cleanup lifecycle

Prefer explicit lifecycle states over immediate deletion:

```text
active -> review -> deprecated -> archived -> removable
```

Not every file needs every state, but deletion should be explainable.

Useful cleanup signals include:

- no inbound references
- superseded by a named replacement
- duplicate content
- generated artifact no longer produced
- obsolete configuration for a removed subsystem
- stale temporary migration files
- empty/placeholder files with no declared purpose

Signals are evidence, not automatic semantic verdicts.

## Cross-repository architecture

The intended long-term shape is:

```text
                    Project Steward / Coherence Steward
                                 |
               shared checks, repair logic, reporting
                                 |
            +--------------------+--------------------+
            |                                         |
   Root-Sequence/.github                       Dev11 .github
   templates/adapters                         templates/adapters
            |                                         |
      Root Sequence repos                         Dev11 repos
            \                                         /
             +----------- other project repos -------+
```

Organization `.github` repositories should stay thin. A dedicated stewardship implementation repository should own the reusable engine, schemas, tests, and actions so maintenance logic is not copied across projects.

## Adoption

Adopt incrementally.

1. Add a maintenance manifest to one repository.
2. Automate deterministic documentation/index synchronization.
3. Add link/file/reference audits.
4. Add change-impact reporting.
5. Add conservative stale/orphan review signals.
6. Generalize the pattern into the shared steward engine.
7. Roll the shared workflow into additional repositories.

A repository that has not adopted stewardship should continue working normally.

## Human goal

A healthy project should require less remembering over time, not more.

The maintenance layer exists so people can spend attention on exploration, learning, building, revising, connecting ideas, and adapting to new constraints instead of repeatedly reconstructing what routine maintenance was forgotten.
